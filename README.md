# Dayflow — дэшборд продуктивности

Дэшборд хранит годовые, месячные, недельные и дневные цели, задачи, статусы и дедлайны. После входа данные сохраняются локально и синхронизируются с Supabase между устройствами.

## Запуск

Нужен Node.js `20.19+` или `22.12+`. Откройте терминал в папке проекта:

```powershell
npm.cmd install
npm.cmd run dev
```

Откройте адрес Vite, обычно `http://localhost:5173/`.

## Настройка Supabase

1. Создайте проект на [supabase.com](https://supabase.com/).
2. В панели проекта откройте **Project Settings → API** и скопируйте **Project URL** и **Publishable key**. В браузерном приложении используется только публичный ключ; `service_role` здесь не нужен и не должен попадать в клиентский код.
3. Скопируйте `.env.example` в `.env.local` в корне проекта и заполните значения:

   ```env
   VITE_SUPABASE_URL=https://your-project-id.supabase.co
   VITE_SUPABASE_PUBLISHABLE_KEY=ваш-публичный-ключ
   ```

   `.env.local` автоматически исключён из Git. Vite читает переменные с префиксом `VITE_` и включает их в клиентскую сборку, поэтому здесь допустим только публичный publishable/anon key.

4. В Supabase откройте **SQL Editor → New query**, вставьте и выполните содержимое `supabase/migrations/20261023000000_dashboard_sync.sql`. Миграция создаёт таблицы владельцев, цели и задачи, включает RLS и атомарную RPC-синхронизацию с проверкой версии.
5. В **Authentication → URL Configuration** укажите адрес приложения в **Site URL** и добавьте его в **Redirect URLs** (например, `http://localhost:5173/**`). Если подтверждение почты включено, подтвердите адрес из письма перед входом.
6. Перезапустите Vite после создания `.env.local`: `npm.cmd run dev`. Зарегистрируйтесь или войдите в интерфейсе дэшборда.

Пользовательские таблицы имеют `user_id` и политики RLS на чтение, добавление, изменение и удаление. Внешние ключи не позволяют связать задачу или подцель с записью другого владельца. RPC-синхронизация выполняется от имени вошедшего пользователя и проверяет ожидаемую ревизию; конфликт между устройствами не перезаписывает сервер молча.

## Перенос и работа без сети

При первом входе существующие локальные данные не отправляются автоматически. Если локальные данные найдены, интерфейс предложит импортировать или объединить их с серверными. Если записи с одинаковым ID различаются, сохраняются обе версии: локальной записи назначается новый ID, а связи целей и задач обновляются. Если выбрать серверную версию, локальная копия предварительно сохраняется в браузере как резервная.

Изменения сначала сохраняются в локальной копии пользователя. При отсутствии сети они помечаются как ожидающие синхронизации и отправляются после восстановления подключения. Если сервер изменился параллельно, пользователь выбирает серверную версию либо явно подтверждает замену сервера текущей локальной версией.

## Загрузка в GitHub или другой Git-хостинг

Создайте пустой репозиторий на выбранном Git-хостинге. В терминале, открытом в папке `productivity-dashboard`, проверьте исключение `.env.local`, затем добавьте файлы и привяжите удалённый репозиторий:

```powershell
git check-ignore .env.local
git init -b main
git add .
git status --short
git commit -m "Prepare productivity dashboard"
git remote add origin https://github.com/ВАШ-АККАУНТ/ВАШ-РЕПОЗИТОРИЙ.git
git push -u origin main
```

Перед коммитом убедитесь, что `.env.local`, `node_modules` и `dist` не отображаются среди добавляемых файлов. В репозиторий включайте `.env.example`, но никогда не используйте `git add -f` для `.env.local`. Если GitHub попросит войти, используйте его обычную авторизацию или Git Credential Manager.
