# Dayflow — дэшборд продуктивности

Итоговая проверка административного раздела, исправление блокировки и действия для Vercel/Supabase: [ADMIN_REVIEW.md](./ADMIN_REVIEW.md).

Дэшборд хранит годовые, месячные, недельные и дневные цели, задачи, статусы и дедлайны. После входа данные сохраняются локально и синхронизируются с Supabase между устройствами.

## Запуск

Нужен Node.js `20.19+` или `22.12+`. Откройте терминал в папке проекта:

```powershell
npm.cmd install
npm.cmd run dev
```

Откройте адрес Vite, обычно `http://localhost:5173/`.

## Настройка Supabase

1. Создайте проект на [supabase.com](https://supabase.com/).
2. В панели проекта откройте **Project Settings → API** и скопируйте **Project URL** и **Publishable key**. В браузерном приложении используется только публичный ключ; `service_role` здесь не нужен и не должен попадать в клиентский код.
3. Скопируйте `.env.example` в `.env.local` в корне проекта и заполните значения:

   ```env
   VITE_SUPABASE_URL=https://your-project-id.supabase.co
   VITE_SUPABASE_PUBLISHABLE_KEY=ваш-публичный-ключ
   ```

   `.env.local` автоматически исключён из Git. Vite читает переменные с префиксом `VITE_` и включает их в клиентскую сборку, поэтому здесь допустим только публичный publishable/anon key.

4. В Supabase откройте **SQL Editor → New query** и выполните миграции в порядке:
   - `supabase/migrations/20261023000000_dashboard_sync.sql`
   - `supabase/migrations/20261024000000_workspaces.sql`
   - `supabase/migrations/20261025000000_workspace_task_comments.sql`
   - `supabase/migrations/20261026000000_friends.sql`
   - `supabase/migrations/20261027000000_workspace_friend_invites.sql`
   - `supabase/migrations/20261028000000_workspace_history.sql`
   - `supabase/migrations/20261029000000_workspace_roles.sql`
   - `supabase/migrations/20261030000000_workspace_archive.sql`
   - `supabase/migrations/20261031000000_friend_lookup_email_fix.sql`
   - `supabase/migrations/20261032000000_usernames.sql` (уникальные username, таблица `profiles` с RLS)
   - `supabase/migrations/20261033000000_task_recurrence.sql` (повторяющиеся задачи: колонка `tasks.recurrence`, обновлённый `sync_dashboard`)
   - `supabase/migrations/20261034000000_task_reschedule.sql` (история переноса: `moved_from`, `moved_at`, `move_count`, обновлённый `sync_dashboard`)
   - `supabase/migrations/20261035000000_task_reminders.sql` (настройки напоминаний на личных задачах, обновлённый `sync_dashboard`)
   - `supabase/migrations/20261036000000_signup_username.sql` (создаёт профиль с уникальным username при регистрации)
   - `supabase/migrations/20261037000000_personal_archive.sql`
   - `supabase/migrations/20261038000000_admin_foundation.sql` (закрытая конфигурация единственного администратора и проверка прав в БД)
   - `supabase/migrations/20261039000000_admin_overview.sql` (RPC обзора админ-панели)
   - `supabase/migrations/20261040000000_admin_user_management.sql` (управление пользователями, блокировка, журнал действий)
   - `supabase/migrations/20261041000000_admin_workspace_support.sql` (поддержка пространств: состав, приглашения, восстановление владельца)
   - `supabase/migrations/20261042000000_admin_record_lookup.sql` (диагностический поиск целей и задач, только чтение)
   - `supabase/migrations/20261043000000_admin_invitations_health.sql` (срок действия приглашений, админ-список приглашений, состояние сайта и журнал ошибок)
   - `supabase/migrations/20261101000000_immutable_admin_audit.sql` (неизменяемый журнал, автоматические события и фильтры)
   - `supabase/migrations/20261101000001_admin_audit_api_compatibility.sql` (совместимость со старым клиентом)

5. В **Authentication → URL Configuration** укажите адрес приложения в **Site URL** и добавьте его в **Redirect URLs** (например, `http://localhost:5173/**`). Если подтверждение почты включено, подтвердите адрес из письма перед входом.
6. Перезапустите Vite после создания `.env.local`: `npm.cmd run dev`. Зарегистрируйтесь или войдите в интерфейсе дэшборда.

При регистрации теперь обязательно задаётся уникальный username. Чтобы профили создавались при подтверждении аккаунта, выполните миграции `20261032000000_usernames.sql` и `20261036000000_signup_username.sql` (все миграции запускаются по порядку). Изменение существующего username доступно через кнопку настроек рядом с email в шапке.

Пользовательские таблицы имеют `user_id` и политики RLS на чтение, добавление, изменение и удаление. Внешние ключи не позволяют связать задачу или подцель с записью другого владельца. RPC-синхронизация выполняется от имени вошедшего пользователя и проверяет ожидаемую ревизию; конфликт между устройствами не перезаписывает сервер молча. Локальные копии хранятся с ключом пользователя; старые несвязанные с аккаунтом локальные данные один раз закрепляются за первым вошедшим пользователем в этом браузере и не предлагаются следующим аккаунтам.

Пространства и общие записи защищены отдельными политиками RLS: читать и изменять их могут только участники. Комментарии к общей задаче доступны участникам её пространства, автор может изменять и удалять свои комментарии, владелец пространства может удалять любой комментарий. Назначение ссылается только на участника того же пространства; при выходе или удалении участника назначение автоматически сбрасывается через `ON DELETE SET NULL`. Личные таблицы задач остаются отдельными, комментарии доступны только через таблицу общих задач. Изменение ролей, создание/удаление пространства, приглашение и принятие приглашений выполняются проверяемыми функциями базы данных; клиент не получает `service_role` и не может напрямую назначить себе членство или роль. Приглашение вводится по email существующего пользователя и появляется у него во вкладке **Пространства** после входа. Email-уведомления не отправляются: для них отдельно понадобится настроить почтовый сервис и серверную функцию, секреты которой нельзя размещать в клиентском приложении. Список пользователей Supabase в интерфейсе не раскрывается (кроме админ-панели, см. ниже).

### Администратор

Глобальный администратор — отдельное понятие от ролей `owner`/`admin` рабочего пространства. Миграция `20261038000000_admin_foundation.sql` создаёт закрытую таблицу `private.admin_config` с единственной возможной строкой. В ней хранится точный UUID из `auth.users`; API-роли не имеют права читать или изменять эту таблицу. Проверка `private.is_admin()` использует `auth.uid()` из проверенного Supabase JWT, не принимает `user_id` от клиента и возвращает `false`, пока администратор не настроен. RPC `public.is_current_user_admin()` безопасно возвращает текущему вошедшему пользователю только `true` или `false`.

После применения миграций:

1. В Supabase откройте **Authentication → Users**, найдите свой существующий аккаунт и скопируйте его **User ID** (UUID), а не email.
2. В **SQL Editor** выполните запрос, заменив строку на скопированный UUID:

   ```sql
   insert into private.admin_config (singleton, admin_user_id)
   values (true, 'ВСТАВЬТЕ-SUPABASE-USER-UUID')
   on conflict (singleton) do nothing;
   ```

   Запускайте запрос в панели Supabase с привилегиями владельца проекта, не из приложения и не из браузера. `ON CONFLICT DO NOTHING` не меняет уже назначенного администратора. Не добавляйте UUID или секреты в `VITE_*`, исходный код или клиентскую сборку.

3. Войдите в приложение этим аккаунтом. Для серверной проверки используйте `supabase.rpc("is_current_user_admin")`: результат должен быть `true` только для назначенного UUID. Сам по себе этот RPC годится для отображения интерфейса, но не заменяет проверку разрешений на каждой операции.

Политика RLS `profiles_select_admin` разрешает этому аккаунту читать только таблицу профилей (UUID и username; email в ней нет). Для `goals`, `tasks`, ревизий, рабочих пространств и других данных сохраняются действующие ограничения: обычный пользователь и администратор видят личные записи только своего `auth.uid()`. Административную операцию над другой таблицей следует добавлять отдельно: проверять `private.is_admin()` в её RLS-политике или в серверной RPC-функции с проверкой прав и дать минимум необходимых операций. Не используйте переданный клиентом UUID и не отключайте RLS. В приложении нет интерфейса назначения/передачи глобальной роли; существующие операции передачи владельца рабочего пространства не изменяют глобального администратора.

Админ-панель доступна по пути `/admin` и через вкладку «Админ» (видна только администратору). Данные отдаёт RPC `public.admin_overview()` из миграции `20261039000000_admin_overview.sql`: она выполняется как `security definer`, сама проверяет `private.is_admin()` и возвращает только счётчики пользователей, целей, задач, пространств и типы недавних событий со временем (без email, имён и содержимого). При деплое на статический хостинг настройте fallback `/admin` → `index.html`.

#### Управление пользователями

Миграция `20261040000000_admin_user_management.sql` добавляет в `/admin` раздел пользователей. Все операции — `security definer` RPC, которые проверяют `private.is_admin()` по `auth.uid()`; `service_role` в браузер не передаётся.

- `admin_list_users` — поиск по username/имени или точному UUID, постранично. Возвращает имя, username, дату регистрации, статус и число целей, задач и пространств. Email, пароли, токены и содержимое записей не возвращаются.
- `admin_set_user_blocked` — блокировка/разблокировка через `auth.users.banned_until`; при блокировке закрываются сессии. Нельзя заблокировать себя и администратора. Причина — до 200 символов.
- `admin_audit_events` — журнал действий; записи хранятся в закрытой таблице `private.admin_audit_log`.
- Удаление аккаунтов не реализовано намеренно.

#### Поиск целей и задач

Миграция `20261042000000_admin_record_lookup.sql` добавляет `admin_find_records(p_query, p_reason)` — поиск только для чтения по точному username, UUID пользователя или ID записи (личные и общие цели/задачи, до 50 строк). Возвращаются владелец, тип, название, дата, статус, область (личное/пространство), признак архива; заметки, комментарии и email не возвращаются. Функция требует причину и пишет каждый поиск в `private.admin_audit_log` (`search_records`). Изменение и удаление записей администратору намеренно недоступны.

Миграция `20261043000000_admin_invitations_health.sql`:

- **Приглашения.** Добавлен `workspace_invitations.expires_at` (14 дней; существующие получили `created_at + 14 дней`) и статус `expired`. Просроченное приглашение нельзя принять, отправитель может выслать новое (старое помечается `expired`). `admin_list_invitations` показывает статус, отправителя, получателя, пространство, дату отправки и срок без email. Администратор может только отменить приглашение (`admin_cancel_workspace_invitation`, обязательны подтверждение и причина ≥3 символов; запись в журнал). Принять приглашение за пользователя нельзя: `respond_to_workspace_invitation` работает только для получателя.
- **Состояние сайта.** `admin_health(p_hours, p_category)` возвращает время последней синхронизации (`dashboard_revisions.synced_at`, ставится триггером), число синхронизаций за 24 ч и последние ошибки. Таблица `private.client_error_log` закрыта от API; клиент пишет в неё только через `report_client_error`, передавая категорию (`sync`, `realtime`, `load`, `local_storage`) и короткий технический код — без текстов ошибок, токенов и данных. Лимит 10 событий в час на пользователя, неавторизованные и заблокированные игнорируются, записи старше 30 дней удаляются автоматически. Доступность Auth проверяется запросом к `/auth/v1/health` с публичным ключом.

#### Управление рабочими пространствами

Миграция `20261041000000_admin_workspace_support.sql` добавляет раздел «Рабочие пространства» в `/admin`. Все функции — `security definer`, проверяют `private.is_admin()` по `auth.uid()`; `service_role` в браузер не передаётся.

- `admin_list_workspaces` — поиск по названию, владельцу или ID; показывает название, владельца, число участников, целей, задач и ожидающих приглашений. Содержимое целей/задач и комментарии не возвращаются.
- `admin_workspace_details` — состав (роль, дата, признак блокировки) и приглашения без email.
- `admin_cancel_workspace_invitation` — отмена только зависшего (`pending`) приглашения.
- `admin_restore_workspace_owner` — назначение владельцем только текущего незаблокированного участника; прежний владелец становится `admin` пространства. Участников функция не добавляет и не удаляет.
- Обе изменяющие функции требуют `p_confirm = true` (в интерфейсе — окно подтверждения и поле причины) и пишут в `private.admin_audit_log` (действия `cancel_invitation`, `restore_owner`, название пространства сохраняется в записи).

Политика блокировки: заблокированный не может войти или обновить сессию (штатно по `banned_until`); выданный access token живёт до истечения, но RESTRICTIVE RLS-политики «Blocked users have no access» сразу закрывают доступ к данным основных таблиц. Security definer RPC пространств RLS обходят и этой политикой не покрыты; их закрывает закрытие сессии.

Проверка после настройки: войдите в аккаунт администратора и убедитесь, что RPC возвращает `true` и запрос к `profiles` показывает профили; затем войдите обычным аккаунтом — RPC должен вернуть `false`, вкладки «Админ» нет, `/admin` перенаправляет на главную, `admin_list_users`/`admin_set_user_blocked` отвечают ошибкой `42501`, а запрос к `profiles` показывает только его собственную строку. Проверяйте через реальную пользовательскую сессию приложения: SQL Editor использует привилегированную роль и не моделирует ограничения браузерного пользователя. Блокировку проверяйте на тестовом аккаунте.

Архив распространяется только на общие цели и задачи рабочего пространства. Архивировать и восстанавливать записи могут владелец и администраторы; это проверяет база данных. Архив сохраняет саму запись, связи, комментарии и историю, а также идентификатор архивировавшего и время. В пространстве есть отдельный поиск и фильтры по типу/статусу, участнику и дате архивации. Личные цели и задачи этой функцией не затрагиваются.

В активном пространстве командный обзор строится только по общим записям Supabase за выбранный период. Каждая неархивная задача учитывается один раз по её дате: процент выполнения — выполненные задачи, делённые на все задачи периода. Для непересекающихся статусов задача считается либо выполненной, либо просроченной незавершённой, либо активной («В процессе»), либо ожидающей выполнения. Просрочка определяется по сроку, а если он не задан — по времени задачи или концу указанного дня в локальном часовом поясе браузера. Прогресс цели вычисляется по связанным с ней общим задачам и подцелям.

Новые цели и задачи создаются из личного дэшборда с явным выбором **Личное** или конкретного пространства. Существующая личная задача переносится/копируется только через отдельное действие с подтверждением; при переносе личная запись удаляется лишь после сохранения общей. Общие записи также можно создавать непосредственно в открытом пространстве. Участники могут редактировать общие данные, а задачи назначать участникам. Изменения общих данных обновляются в открытом пространстве в реальном времени при включённом Supabase Realtime.

## Перенос и работа без сети

При первом входе существующие локальные данные не отправляются автоматически. Если локальные данные найдены, интерфейс предложит импортировать или объединить их с серверными. Если записи с одинаковым ID различаются, сохраняются обе версии: локальной записи назначается новый ID, а связи целей и задач обновляются. Если выбрать серверную версию, локальная копия предварительно сохраняется в браузере как резервная.

Изменения сначала сохраняются в локальной копии пользователя. При отсутствии сети они помечаются как ожидающие синхронизации и отправляются после восстановления подключения. Если сервер изменился параллельно, пользователь выбирает серверную версию либо явно подтверждает замену сервера текущей локальной версией.

## Просроченные задачи и перенос

Вкладка «Просрочено» в панели задач показывает личные незавершённые задачи, срок которых (дедлайн или дата) уже прошёл. Задачу можно перенести на завтра, на понедельник следующей недели или на выбранную дату, либо отметить несколько и перенести разом: перед этим показывается число задач, а после — кнопка «Отменить перенос». Перенос меняет дату существующей задачи (копии не создаются), запоминает прежнюю дату и число переносов. Дедлайн сдвигается, если оказался раньше новой даты; связь с целью снимается, если новая дата вне срока цели. Для повторяющихся задач переносится только выбранный экземпляр (за последние 30 дней), правило не меняется. Задачи рабочих пространств сюда не входят.

## Поиск, фильтры и сортировка задач

В таблице задачи ищутся по названию и заметкам. Комбинируемые фильтры позволяют выбрать статус (все, активные, выполненные, просроченные), приоритет, цель, наличие срока и область дат — текущий период или все даты. Для повторяющихся задач в режиме «Все даты» учитывается скользящий год истории, чтобы не создавать неограниченное число экземпляров. Активные фильтры видны отдельными метками; их можно снимать по одному или сбросить вместе с поиском. Заголовки названия, даты/времени, приоритета и статуса сортируют в обе стороны с индикатором направления. Фильтры хранятся только в памяти страницы.

## Аналитический обзор

Панель «Прогресс» считает личные задачи за неделю или месяц относительно выбранной даты. Запланированной считается каждая задача с датой в периоде, а повторяющиеся задачи учитываются по отдельным экземплярам. Процент — выполненные со статусом «Выполнено» от всех запланированных задач. Просроченные — незавершённые задачи с прошедшим дедлайном (или датой задачи, если дедлайна нет). Переносы считают записи/экземпляры, перенесённые в период по сохранённым данным. Прогресс целей рассчитан по связанным задачам в том же периоде и целям, пересекающим его. Сравнение показывается, только если есть данные за предыдущий такой же период. Все календарные границы используют локальные даты; для пустых периодов и малой выборки интерфейс сообщает, что вывод основан на доступных задачах. Статистика вычисляется из уже существующих данных, миграция не нужна.

## Напоминания

У личной задачи можно выбрать «Без напоминания», «В назначенное время» или за 5/15/30/60 минут либо за день до срока. Временем считается дедлайн, а при его отсутствии — указанное время задачи; без времени напоминание не включается. Разрешение браузера запрашивается только по нажатию «Включить уведомления». Уведомления браузера и список ближайших напоминаний работают, пока приложение открыто; фоновой доставки после закрытия сайта нет. Глобальный переключатель хранится локально для аккаунта и текущего браузера, а правило задачи — в Supabase с RLS личной таблицы. Общие задачи пространств пока не включены в напоминания. Для новой схемы нужно выполнить миграцию `20261035000000_task_reminders.sql`.

## Календарь

В панели «Задачи» переключатель «Таблица / Календарь» показывает личные задачи по месяцу, неделе или дню (переходы ‹ ›, «Сегодня», выбор даты). Задачи со временем стоят в часовых слотах дня, без времени — в блоке «Без времени». Задачи на одно время показываются обе с значком конфликта. Длительность не хранится, поэтому задача занимает слот начала. Перенос перетаскиванием выполняется после подтверждения; повторяющиеся задачи открываются для правки серии. Миграция не нужна.

## Загрузка в GitHub или другой Git-хостинг

Создайте пустой репозиторий на выбранном Git-хостинге. В терминале, открытом в папке `productivity-dashboard`, проверьте исключение `.env.local`, затем добавьте файлы и привяжите удалённый репозиторий:

```powershell
git check-ignore .env.local
git init -b main
git add .
git status --short
git commit -m "Prepare productivity dashboard"
git remote add origin https://github.com/ВАШ-АККАУНТ/ВАШ-РЕПОЗИТОРИЙ.git
git push -u origin main
```

Перед коммитом убедитесь, что `.env.local`, `node_modules` и `dist` не отображаются среди добавляемых файлов. В репозиторий включайте `.env.example`, но никогда не используйте `git add -f` для `.env.local`. Если GitHub попросит войти, используйте его обычную авторизацию или Git Credential Manager.


## Неизменяемый журнал административных действий

`20261101000000_immutable_admin_audit.sql` применяется после всех миграций `20261043…`. Номер выбран для сохранения порядка после прежних файлов с некалендарными датами. В подключённом проекте эта миграция уже применена через MCP под версией `20261031085610` и именем `immutable_admin_audit`; повторно выполнять её там не нужно. Как и у предыдущих административных миграций, локальный номер отличается от автоматически выданного MCP номера; перед переходом на `db push` нужно отдельно согласовать историю миграций.

Триггеры базы автоматически фиксируют действия единственного администратора: блокировку/разблокировку, добавление/удаление/изменение участников, смену владельца, отмену приглашения и изменения целей, задач, комментариев, профилей и пространств. Обычные пользовательские изменения не создают административных событий. Смена владельца включает отдельные события изменения ролей участников. Повторная запись идентичных значений не создаёт события. Полномочия на изменение пользовательских записей эта миграция не расширяет.

Событие содержит действие, серверное время, UUID администратора, тип/ID объекта, ID связанного пользователя/пространства, операцию INSERT/UPDATE/DELETE и причину. Новые события не сохраняют названия пространств, запрос поиска, тексты записей, старые/новые значения, email, пароли или токены. Для административных RPC причина обязательна (3–200 символов); строки с распространёнными признаками секретов отклоняются. Автоматические изменения через существующие операции пространства получают причину «Изменение администратором», если доверенный серверный код не задал причину в локальном параметре транзакции `app.admin_audit_reason`. Произвольную строку причины нельзя считать надёжно очищенной от любых персональных данных: вводите только краткое основание без секретов. Старые события сохраняют исходные поля; недостающие ID не выдумываются.

`private.admin_audit_log` защищена RLS: SELECT разрешён только действующему администратору; запись через клиент запрещена всем, включая администратора. Публичного RPC для вставки событий нет. Триггеры получают идентичность из `auth.uid()` и закрытой `private.admin_config`; actor/time не принимаются от клиента. Изменение данных и событие выполняются в одной транзакции: ошибка журнала отменяет изменение. UPDATE/DELETE/TRUNCATE запрещены также триггерами. Владелец БД с правами на изменение схемы технически может снять защиту — это граница доверия, журнал не является внешним WORM-хранилищем.

`admin_audit_search` работает как SECURITY INVOKER, использует RLS и поддерживает полуоткрытый интервал дат `[from, to)`, действие, тип объекта, точный ID объекта/пользователя/пространства и страницы по 20 событий. В интерфейсе время отображается в локальном часовом поясе администратора.

SQL-проверка: выполнить `supabase/tests/admin_audit.sql` целиком через привилегированное соединение SQL Editor/MCP на базе с настроенным `private.admin_config`. Она создаёт временного пользователя и пространство, выполняет настоящие RPC под ролью `authenticated`, проверяет автоматические события, фильтры, отсутствие содержимого записей, запрет подделки и изменений журнала, RLS для обычного пользователя, недоверенность `user_metadata` и запрет анонимного доступа. Все тестовые изменения откатываются через ROLLBACK. Проверка выполнена на подключённом проекте: PASS; тестовых аккаунтов после неё нет.

Миграция `20261101000001_admin_audit_api_compatibility.sql` сохраняет прежний `admin_audit_events(p_limit)` с ответом-массивом для уже открытых старых клиентов; новый интерфейс вызывает отдельный `admin_audit_search`. Обе функции используют RLS и не предоставляют записи в журнал.
