Изменения интерфейса находятся в рабочей папке. Изменение безопасности базы уже применено в подключённом Supabase. Публикация в Vercel в этой сессии не выполнялась.

## Что исправлено

- Разделы «Обзор», «Пользователи», «Пространства», «Приглашения», «Поиск записей», «Состояние сайта», «Журнал» открываются отдельно. Неактивные разделы не запрашивают данные. Сохранены цвета, поверхности, скругления и тёмная тема сайта; административная область выделена рамкой и подписью.
- Таблица пользователей превращается в карточки на узком экране. Увеличены области нажатия, предусмотрены перенос длинных ID, мобильные поля и прокрутка окна подтверждения.
- Поиск пользователей и пространств имеет сброс и количество результатов. Сохранены серверные страницы, фильтры приглашений, журнала и технических ошибок. Добавлена проверка границ периода журнала. Исправлены гонки запросов приглашений, состояния сайта и обзора.
- Блокировка/разблокировка, смена владельца и отмена приглашения используют окно с объектом, ID, текущим/новым состоянием и последствиями. Причина обязательна; повторная отправка и закрытие во время запроса запрещены. Диалог поддерживает Escape, удержание фокуса средствами native dialog и возврат фокуса. Ошибка оставляет диалог открытым.
- Доступ, ошибки, пустые результаты, загрузка и обновление имеют отдельные сообщения. Административные ошибки не выводят необработанные сообщения, details и hints сервера.
- Исправление содержимого записей и необратимое удаление не добавлены. Поиск записей остаётся только для чтения, по точному идентификатору/username и с обязательным аудитом причины. Заметки и комментарии не возвращаются.

## Исправление безопасности Supabase

Обнаружен обход блокировки через SECURITY DEFINER: ограничения RLS не останавливали вызовы некоторых RPC с ещё действующим access token. Миграция `admin_access_hardening`, версия **20261031141449**, применена через подключённый MCP после проверки в транзакции с откатом.

Точная копия SQL: `supabase/patches/20261031141449_admin_access_hardening.sql`. Она добавляет проверку блокировки в существующие публичные PL/pgSQL SECURITY DEFINER RPC, исключая триггеры; сохраняет их аргументы, тела, владельцев и grants. Повторное выполнение пропускает уже добавленные проверки. `private.is_admin()` теперь также отказывает заблокированному закреплённому аккаунту. Таблица истории пространств получила ограничивающую политику блокировки. У клиентских ролей отозван EXECUTE внутренних функций-триггеров. Конфигурация администратора осталась закрытой для записи клиентом.

Будущие RPC должны явно проверять блокировку: этот SQL изменяет существующие функции, а не автоматически защищает будущие определения.

## Серверный доступ к /admin на Vercel

`api/admin.js` проверяет access token через Supabase Auth и `is_current_user_admin` на каждом GET/POST. Для входа из интерфейса POST устанавливает cookie на 5 минут с HttpOnly, Secure, SameSite=Strict и префиксом __Host-. GET /admin повторяет обе проверки, затем отдаёт собранную оболочку; без прав возвращает 401/403, при сбое — 503. Cookie не заменяет проверки прав в SQL/RLS. Ответы не кешируются. POST/DELETE требуют совпадения Origin и Host; выход очищает cookie. Обработчик не выводит токены и серверные ошибки в логи. Административные RPC вызываются с JWT пользователя, service_role не используется.

`vercel.json` направляет /admin и вложенные пути в этот обработчик и включает dist/index.html в функцию. Пути ресурсов сборки сделаны абсолютными. В Vite dev сервер Vercel не запускается: доступ к данным по-прежнему проверяется Supabase, но HTTP-проверка самого пути проверяется отдельными тестами обработчика.

SQL-проверки используют временных пользователей и настоящие RPC под ролями authenticated/anon в привилегированной тестовой транзакции. Все изменения откатываются через ROLLBACK. Правила приложения и RLS не отключаются. Эти проверки не заменяют вход через реальный браузер и HTTP-проверку регистрации, подтверждения почты, пароля и обновления сессии.

Обработчик Vercel тестируется с изолированными ответами Auth/RPC: проверены 401 без сессии, 403 обычному пользователю, поддельный JWT, утрата прав после выдачи cookie, защита Origin, выдача и очистка cookie, серверная выдача HTML и безопасная ошибка сети. Реальные ограничения базы отдельно проверены SQL-тестами.

Серверный обработчик ещё не подтверждён на размещении Vercel.
2. **Supabase:** новую миграцию повторно применять в подключённом проекте не нужно. Для другой базы сначала выполнить существующие миграции до `admin_audit_api_compatibility`, затем SQL из `supabase/patches/`. Перед автоматическим `supabase db push` согласовать локальную и облачную историю: старые файлы имеют версии 20261038…–20261043… с некалендарными датами и 20261101…, а облачный MCP выдал другие версии. Три таблицы без разрешающих политик закрыты по умолчанию — это не повод выдавать им публичный доступ. Правила advisor: https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable и https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy.

Нельзя подтвердить визуальный результат на широком/мобильном экране или завершённые пользовательские сценарии.
